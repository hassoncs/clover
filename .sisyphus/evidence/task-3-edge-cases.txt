# Task 3: Edge Cases Analysis
# Font rendering edge cases across Godot and React Native layers

================================================================================
EDGE CASE 1: VARIABLE FONTS
================================================================================

Platform Status:
  Godot:  SUPPORTED via FontVariation class (axes: weight, width, slant, custom)
  RN:     NOT RECOMMENDED — Expo docs explicitly warn against variable fonts
  Web:    SUPPORTED via CSS font-variation-settings (Godot web export uses browser)

Edge Case Scenario:
  A game author provides a variable font URL (e.g., Inter[wght].ttf) expecting
  weight interpolation for score displays (thin for labels, bold for numbers).

  - Godot web: Works — browser handles variable font natively
  - Godot native (via react-native-godot): Works — Godot's FontVariation handles it
  - RN overlay (iOS): May partially work — iOS supports variable fonts at OS level,
    but expo-font has no axis control API. Weight may snap to nearest static instance.
  - RN overlay (Android): Unreliable — Android variable font support varies by OS
    version and OEM. Pre-Android 8.0 has no support.

Risk: MEDIUM (platform-limit)
  Variable fonts create a consistency trap: they work in Godot but not reliably in RN.
  Authors who test only in the Godot preview will ship broken overlay typography.

Mitigation Direction:
  Restrict to static fonts in the shared FontConfig type, or provide static fallback
  weights alongside variable font URLs.

================================================================================
EDGE CASE 2: FONT FALLBACK CHAINS
================================================================================

Platform Status:
  Godot:  Single fallback — ThemeDB.fallback_font (hardcoded in TextEffectSystem.gd:83)
  RN:     Platform default — no explicit fallback chain configured
  Web:    CSS font-family stacks (e.g., "Bangers, Impact, sans-serif") — NOT used

Edge Case Scenario:
  A game uses a decorative font ("Creepster") for Halloween theme. The font URL is
  unreachable (CDN outage, CORS issue, offline play).

  - Godot: Falls back to ThemeDB.fallback_font (generic sans-serif). The Halloween
    aesthetic is completely lost. No intermediate fallback like "Impact" or "Courier".
  - RN: fontFamily "Creepster" is unrecognized → platform default (San Francisco/Roboto).
    Same loss of aesthetic, but additionally no warning to the author or player.

Risk: MEDIUM (impl-gap)
  The single-fallback model means any font loading failure produces a jarring visual
  change. There's no "close enough" intermediate fallback.

Negative Scenario:
  A game jam game uses "Press Start 2P" for its pixel aesthetic. During a CDN blip,
  the font fails to load. The game renders in a proportional sans-serif, breaking
  the pixel grid alignment. Score counters that were designed to fit in a fixed-width
  box now overflow because the fallback font has different metrics.

================================================================================
EDGE CASE 3: REMOTE FONT LOADING CONSTRAINTS
================================================================================

Platform Status:
  Godot:  HTTP download via HTTPRequest node (TextEffectSystem.gd:79-114)
  RN:     No remote loading implemented (expo-font supports it but unused)
  Web:    @font-face with URL (Godot web export uses browser font loading)

Edge Case Scenarios:

  A) CORS Restrictions (Web Export):
     Google Fonts URLs include proper CORS headers — they work.
     Self-hosted fonts on a game author's server may lack CORS headers.
     Godot's web export runs in a browser context subject to CORS.
     RESULT: Font silently fails to load; fallback font used; no error surfaced.

  B) Mixed Content (HTTPS page, HTTP font URL):
     If the app is served over HTTPS (production), an HTTP font URL will be blocked
     by the browser's mixed content policy.
     RESULT: Silent failure. Godot's push_warning goes to console, not to the user.

  C) Large Font Files:
     CJK fonts (e.g., Noto Sans CJK) can be 15-20MB. Downloading on every game load
     is wasteful. The current cache (user://fonts/) helps on repeat loads but the
     first load on a slow connection causes a visible delay.
     RESULT: Text appears in fallback font for several seconds, then pops to the
     correct font. No loading indicator exists.

  D) Concurrent Font Downloads:
     If a game definition references 3+ different font URLs, TextEffectSystem creates
     multiple HTTPRequest nodes. There's no download queue or concurrency limit.
     RESULT: On slow connections, multiple parallel downloads may all timeout,
     causing all text to render in fallback fonts.

Risk: MEDIUM (impl-gap + platform-limit mix)
  Remote loading is inherently fragile. The current implementation has no retry logic,
  no timeout configuration, no loading state feedback, and no download prioritization.

EDGE CASE 4: NON-LATIN SCRIPT SHAPING
================================================================================

Platform Status:
  Godot:  TextServerAdvanced provides HarfBuzz + ICU + SIL Graphite
          Supports: Arabic (RTL + joining), Hebrew (RTL), Devanagari (conjuncts),
          Thai (no word boundaries), CJK (vertical layout optional)
  RN:     Delegates to OS text rendering (CoreText on iOS, Skia/HarfBuzz on Android)
          Generally good for common scripts; less tested for complex shaping
  Web:    Browser handles shaping via platform text stack

Edge Case Scenarios:

  A) Arabic Text in Game World (Godot):
     A game displays Arabic text ("مرحبا") in a Label node.
     TextServerAdvanced handles RTL and joining correctly IF the font has Arabic glyphs.
     If the loaded font lacks Arabic coverage, Godot falls back to ThemeDB.fallback_font
     which may or may not have Arabic glyphs depending on the platform.
     RESULT: Potentially broken rendering — boxes (tofu) instead of characters.

  B) Arabic Text in Overlay (RN):
     Same Arabic text in an overlay element. RN delegates to the OS, which handles
     RTL and shaping natively. However, if fontFamily is set to a Latin-only font,
     the OS may or may not fall back to a system Arabic font.
     RESULT: Platform-dependent behavior. iOS generally handles this well (automatic
     font fallback per glyph). Android behavior varies by OEM.

  C) Mixed LTR/RTL in Same Element:
     A score display shows "Score: ١٢٣" (Arabic-Indic numerals).
     Godot's BiDi support handles this. RN's OS-level BiDi handles this.
     But the two layers may render the same string with different BiDi resolution,
     causing visual inconsistency between game-world and overlay text.

  D) Thai/Khmer Without Word Boundaries:
     Thai text has no spaces between words. Line breaking requires dictionary-based
     word segmentation. Godot's ICU integration handles this. RN delegates to OS.
     If a game has Thai text in both layers, line breaks may occur at different
     positions, causing layout differences.

Risk: LOW (platform-limit + impl-gap)
  Non-Latin shaping is theoretically supported by both platforms but completely
  untested in this codebase. No games currently use non-Latin text. The risk is
  low today but becomes HIGH if internationalization is ever pursued.

================================================================================
EDGE CASE 5: FONT FORMAT MISMATCHES ACROSS LAYERS
================================================================================

Platform Status:
  Godot:  TTF, TTC, OTF, OTC, WOFF, WOFF2, Type 1
  RN:     TTF, OTF only (universal); WOFF/WOFF2 on web only
  Web:    All formats via browser

Edge Case Scenario:
  A game author provides a WOFF2 font URL (common for web optimization).
  - Godot (all platforms): Loads successfully
  - RN overlay (web): Loads successfully (browser handles WOFF2)
  - RN overlay (iOS/Android): Fails silently — expo-font cannot decode WOFF2

  RESULT: Game looks correct in web preview and Godot preview, but overlay text
  breaks on native mobile. This is a particularly insidious bug because it only
  manifests on the platform where most users play.

Risk: MEDIUM (platform-limit)
  WOFF2 is the most common web font format. Authors sourcing fonts from the web
  will naturally encounter WOFF2 URLs. The format works everywhere except RN native.

================================================================================
EDGE CASE 6: FONT LOADING RACE CONDITIONS
================================================================================

Edge Case Scenario:
  Game starts → Godot begins downloading font via HTTP → First frame renders with
  fallback font → Font arrives 500ms later → Text pops to correct font.

  Meanwhile, RN overlay renders immediately with system font (no loading at all).

  RESULT: For the first ~500ms, both layers show fallback fonts. Then Godot pops
  to the correct font while RN stays on system font permanently. The visual
  inconsistency is jarring and persists for the entire game session.

Risk: HIGH (impl-gap)
  This is the most visible manifestation of gap #1 (expo-font unused) combined
  with gap #10 (remote loading requires network). Every game with custom fonts
  will exhibit this behavior on first load.

================================================================================
SUMMARY: EDGE CASE RISK MATRIX
================================================================================

| Edge Case                    | Godot Risk | RN Risk | Cross-Layer Risk |
|------------------------------|------------|---------|------------------|
| Variable fonts               | Low        | Medium  | Medium           |
| Fallback chains              | Medium     | Medium  | Medium           |
| Remote loading (CORS)        | Medium     | N/A     | Low              |
| Remote loading (offline)     | Medium     | N/A     | High             |
| Remote loading (large files) | Medium     | N/A     | Low              |
| Non-Latin shaping            | Low        | Low     | Low (today)      |
| Format mismatches (WOFF2)    | None       | Medium  | Medium           |
| Font loading race conditions | Low        | High    | High             |

Highest cross-layer risks:
  1. Font loading race conditions (visible on every custom-font game)
  2. Remote loading offline (breaks game visual identity)
  3. Variable font inconsistency (works in Godot, breaks in RN)
  4. Format mismatches (WOFF2 works everywhere except RN native)
